# 优化验证和测试指南

## 已实施的优化

### 1. 优化 seed 选择策略（高优先级 ✅）

**改动文件：**
- `rag/retrieval/dependency_recall.py`
- `rag/config/retrieval.py`
- `rag/retrieval/retriever.py`
- `rag/retrieval/query_service.py`

**核心改进：**

1. **引入依赖能力评分** (`calculate_dependency_capability_score`)：
   - `dependency_topics` 非空 → +0.3
   - `heading_path` 包含前置规范关键词（说明、规范、配置、错误码等）→ +0.4
   - chunk 类型是 "api" → +0.2
   - `heading_path` 包含通用词（介绍、概述、简介、背景、产品）→ -0.3（**降权干扰文档**）
   - `quality_score` < 0.7 → -0.2

2. **混合排序策略**：
   - `dependency_seed_score = final_score * (1 - weight) + capability_score * weight`
   - 默认 `weight=0.3`，即 70% 召回分数 + 30% 依赖能力评分
   - 按混合分数重新排序后再选择 seed

3. **参数优化**：
   - `seed_score_ratio`: 0.7 → **0.6**（降低阈值，确保关键依赖证据不被过滤）
   - `max_seeds`: 8 → **10**（允许更多 seed）
   - `total_limit`: 12 → **16**（增加依赖证据容量）
   - `final_top_n`: 5 → **8**（增加最终上下文容量）

### 2. 优化上下文组装策略（高优先级 ✅）

**改动文件：**
- `rag/retrieval/dependency_recall.py` (`assemble_dependency_context`)

**核心改进：**

1. **确保高分 seed 进入上下文**：
   - 第一步：优先将高分 seed 加入上下文
   - 第二步：补充常规 TopN（去重）
   - 第三步：追加强制依赖证据

2. **增加强制依赖证据上限**：
   - 新增参数 `max_forced_dependencies=15`
   - 防止依赖证据无限增长的同时，确保关键依赖不被截断
   - 达到上限时记录警告日志

## 测试方案

### 测试用例 1：加解密依赖识别

**目标：** 验证能否正确识别接口与加密说明的依赖关系

**查询：** "生成订单接口如何接入加密？"

**预期结果：**
1. seed 列表包含：
   - "生成订单接口" 的 chunk
   - "加密说明" 的 chunk（即使分数略低于干扰文档）
2. 最终上下文包含完整的加密流程说明（DES 算法、X-Crypto 请求头用法等）
3. 干扰文档（如"产品介绍"）不进入 seed 列表，或排名靠后

**验证方法：**
```bash
# 运行查询
python -m rag.cli.answer_query "生成订单接口如何接入加密？"

# 检查日志输出
# 1. 查看 seed 选择日志，确认包含"加密说明"相关 chunk
# 2. 查看依赖扩展日志，确认新增依赖证据数量 > 0
# 3. 查看最终上下文，确认包含加密流程的完整说明
```

**关键指标：**
- seed 中"加密说明" chunk 的 `dependency_seed_score` 应高于干扰文档
- `dependency_expansion.added_count` > 0
- `dependency_expansion.missing_count` = 0（无缺失依赖）
- 最终上下文长度 > `final_top_n`（有强制依赖证据追加）

### 测试用例 2：干扰文档过滤

**目标：** 验证能否降低干扰文档的权重

**场景：** 索引中包含"产品介绍"、"平台优势"等干扰文档

**查询：** "如何初始化 SDK？"

**预期结果：**
1. 干扰文档的 `dependency_seed_score` 低于业务文档
2. 干扰文档不进入 seed 列表
3. 最终上下文中干扰文档占比 < 20%

**验证方法：**
```bash
python -m rag.cli.answer_query "如何初始化 SDK？"

# 检查日志，分析 seed 选择结果
# 计算干扰文档在最终上下文中的占比
```

**关键指标：**
- "产品介绍" chunk 的 `capability_score` 应为负值（-0.3）
- seed 列表不包含"产品介绍"等干扰文档
- 最终上下文的前 5 个 chunk 都是业务相关内容

### 测试用例 3：依赖完整性

**目标：** 验证关键依赖证据不会被截断

**查询：** "如何排查支付失败的问题？"

**预期结果：**
1. seed 包含"支付失败排查" chunk
2. 依赖证据包含"错误码说明"和"日志规范"
3. 没有 `missing_critical_deps` 警告（未来实施）
4. 强制依赖证据未达到 `max_forced_dependencies` 上限

**验证方法：**
```bash
python -m rag.cli.answer_query "如何排查支付失败的问题？"

# 检查依赖扩展日志
# 确认 truncated_count = 0（无依赖证据被裁剪）
# 确认 added_count > 0（有依赖证据被追加）
```

**关键指标：**
- `dependency_expansion.truncated_count` = 0
- `dependency_expansion.missing_count` = 0
- `forced_dependency_count` > 0（有强制依赖证据追加）
- 最终上下文包含"错误码说明"和"日志规范"

### 测试用例 4：对比测试（A/B 测试）

**目标：** 对比优化前后的效果

**方法：**
1. 准备 10-20 个测试查询（覆盖不同场景：接口接入、配置、排查、概念查询等）
2. 分别用优化前和优化后的配置运行
3. 对比以下指标：
   - seed 选择的准确性（是否包含关键依赖证据）
   - 依赖扩展的覆盖率（`added_count` / 预期依赖数量）

   - 干扰文档的占比

## 参数调优建议

### 如果仍有干扰文档问题

**症状：** 
- seed 列表仍包含"产品介绍"等无关内容
- 最终答案包含大量营销语言

**调整方案：**
```bash
# 进一步提高依赖能力权重
RAG_DEPENDENCY_SEED_CAPABILITY_WEIGHT=0.4  # 从 0.3 → 0.4

# 进一步降低阈值
RAG_DEPENDENCY_SEED_SCORE_RATIO=0.5  # 从 0.6 → 0.5
```

### 如果依赖证据仍然不足

**症状：**
- `dependency_expansion.truncated_count` > 0
- 最终答案缺少关键前置说明

**调整方案：**
```bash
# 增加依赖证据容量
RAG_DEPENDENCY_TOTAL_LIMIT=20  # 从 16 → 20
RAG_DEPENDENCY_MAX_FORCED_DEPS=20  # 从 15 → 20

# 增加最终上下文容量
RAG_RERANK_FINAL_TOP_N=10  # 从 8 → 10
```

### 如果召回性能下降

**症状：**
- 查询响应时间明显增加
- LLM token 消耗大幅上升

**调整方案：**
```bash
# 降低依赖证据容量
RAG_DEPENDENCY_TOTAL_LIMIT=12  # 恢复到 12

# 降低最终上下文容量
RAG_RERANK_FINAL_TOP_N=6  # 降低到 6

# 降低 seed 数量
RAG_DEPENDENCY_MAX_SEEDS=8  # 恢复到 8
```

## 监控指标

建议在生产环境监控以下指标：

### 1. 依赖召回指标
- `seed_count_avg`: 平均 seed 数量（目标：6-10）
- `dependency_added_count_avg`: 平均新增依赖证据数量（目标：> 0）
- `dependency_missing_count_avg`: 平均缺失依赖数量（目标：= 0）
- `dependency_truncated_count_avg`: 平均裁剪依赖数量（目标：= 0）

### 2. 上下文质量指标
- `final_context_length_avg`: 平均最终上下文长度（目标：8-15）
- `forced_dependency_ratio`: 强制依赖证据占比（目标：20%-40%）
- `interference_doc_ratio`: 干扰文档占比（目标：< 10%）

### 3. 性能指标
- `retrieval_latency_p99`: 召回延迟 P99（目标：< 2s）
- `llm_token_usage_avg`: 平均 LLM token 消耗（监控成本）

## 下一步优化（中低优先级）

1. **优化切分逻辑**（方案 1）：
   - 识别不可切分的原子章节（加密说明、错误码等）
   - 动态调整 chunk_size，保持语义完整性
   - 需要重新构建索引

2. **增加干扰文档过滤**（方案 5）：
   - 在索引构建时标记 `quality_score`
   - 在召回阶段过滤 `quality_score < 0.5` 的候选
   - 需要重新构建索引

### 低优先级（长期优化）

3. **优化依赖分析 prompt**（方案 2）：
   - 增加跨 chunk 语义识别能力
   - 传递更多上下文信息（prev_heading_path、next_heading_path 等）
   - 需要重新构建依赖图

4. **依赖完整性校验**（方案 4.2）：
   - 在查询时校验关键 seed 的依赖是否完整
   - 记录警告日志，辅助诊断
   - 作为监控和诊断工具

## 总结

已实施的优化解决了两个核心问题：

1. **seed 选择不准确** → 引入依赖能力评分，降低干扰文档权重
2. **topoN 截断** → 增加上下文容量，确保关键依赖不被截断

建议按照测试方案验证效果，根据实际情况调整参数。如果仍有问题，可以继续实施中低优先级的优化方案。
