# 切分逻辑优化说明

## 优化目标

解决依赖分析无法识别加解密关系的问题，根本原因是固定大小的硬切分导致关键章节（如加密说明、错误码等）被割裂，LLM 看到的是不完整的上下文。

## 优化方案

### 1. 引入"原子章节"概念

**原子章节**：具有强语义完整性的章节，应作为一个整体保留，不应被切分。

**识别规则**：标题（任意级别）包含以下关键词之一：
- `加密`、`解密`、`签名`、`验证`
- `认证`、`授权`、`鉴权`
- `错误码`、`状态码`
- `参数说明`、`字段说明`
- `示例`、`样例`、`demo`
- `规范`、`约定`、`协议`

### 2. 原子章节处理逻辑

```python
# 伪代码
for block in markdown_blocks:
    if is_heading(block) and is_atomic_section(block) and not in_atomic_section:
        # 1. 提交之前的常规内容
        flush_current_chunk()
        
        # 2. 进入原子章节模式
        in_atomic_section = True
        atomic_section_level = get_heading_level(block)  # 记录顶层级别
        atomic_section_blocks = [block]
    
    elif in_atomic_section and is_heading(block):
        current_level = get_heading_level(block)
        
        if current_level <= atomic_section_level:
            # 遇到同级或更高级标题，原子章节结束
            # 3. 提交整个原子章节（不论大小）
            if tokens <= ATOMIC_SECTION_MAX_TOKENS:
                flush_atomic_section()  # 作为一个完整 chunk
            else:
                # 原子章节过大（>2048 tokens），降级为常规切分
                fallback_to_normal_chunking()
            
            # 4. 退出原子章节模式
            in_atomic_section = False
        else:
            # 子标题，继续累积
            atomic_section_blocks.append(block)
    
    elif in_atomic_section:
        # 在原子章节内，持续累积
        atomic_section_blocks.append(block)
    
    else:
        # 常规切分逻辑（chunk_size=512）
        normal_chunking_logic()
```

### 3. 关键设计点

#### (1) 只在非原子章节内触发新原子章节

```python
if is_heading and not in_atomic_section and is_atomic_section_heading(block):
    # 开始新原子章节
```

**为什么？** 防止子标题（如"### 加密步骤"）再次触发原子章节开始，导致父章节被截断。

#### (2) 记录原子章节的标题级别

```python
atomic_section_level = get_heading_level(block)  # 例如 ## = 2
```

**作用：** 判断何时结束原子章节。只有遇到同级（`##`）或更高级（`#`）标题时才结束，低级标题（`###`、`####`）继续累积。

#### (3) 设置上限保护

```python
ATOMIC_SECTION_MAX_TOKENS = 2048
```

**为什么？** 防止原子章节过大（如包含大量示例代码），导致单个 chunk 超出 LLM 上下文窗口。超过上限时降级为常规切分。

### 4. 配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `chunk_size` | 512 | 常规切分的目标大小 |
| `chunk_overlap` | 100 | 切分时的重叠 tokens |
| `ATOMIC_SECTION_MAX_TOKENS` | 2048 | 原子章节的上限，超过后降级 |

## 优化效果

### 优化前

```
Chunk 1: ## 加密说明 + ### DES 加密算法 (tokens=50)
Chunk 2: ### 加密步骤 (tokens=30)
Chunk 3: ### 请求头设置 (tokens=40)
Chunk 4: ### 示例代码 (tokens=60)
```

**问题：** 加密说明被切分成 4 个 chunk，LLM 在构建依赖图时无法看到完整的加密规范。

### 优化后

```
Chunk 1: ## 加密说明（包含所有子章节）(tokens=107)
  - ### DES 加密算法
  - ### 加密步骤
  - ### 请求头设置
  - ### 示例代码
```

**效果：** 加密说明作为一个完整的 chunk，LLM 可以准确建立"生成订单接口 → 依赖 → 加密说明"的关系。

## 预期改进

1. **依赖图质量提升**：LLM 看到完整的加密说明，可以准确识别"生成订单接口"依赖"加密说明"
2. **召回精度提升**：关键的前置规范（加密、认证、错误码）不会被切分，更容易被召回
3. **上下文完整性提升**：即使向量分数不高，强制依赖证据机制也能确保完整的加密章节进入上下文

## 后续优化方向

1. **动态调整原子章节关键词**：根据实际文档类型（API 文档、技术规范、用户手册）调整关键词列表
2. **章节重要性评分**：结合标题级别、内容长度、关键词密度等因素，动态决定是否作为原子章节
3. **跨章节依赖检测**：识别章节间的引用关系（如"详见加密说明"），增强依赖图准确性
