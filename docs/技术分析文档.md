# 技术分析文档

## 1. 文档目标

本文档从技术实现角度说明当前 RAG 项目的模块划分、职责边界、核心数据流和主要风险。当前版本已反映本次重构后的目录结构、命令入口和完整查询闭环。

## 2. 项目定位

当前项目聚焦于“本地知识库检索增强”场景，核心目标是：

- 将 Word/Confluence 等异构技术文档清洗为统一 Markdown
- 构建面向中文技术文档的多路索引
- 对用户问题提供稳定的召回、重排和最终答案输出
- 为后续服务化和评测闭环保留可扩展结构

相比重构前版本，项目已从“检索基础设施”推进到“可直接回答问题的 RAG 原型”。

## 3. 重构后的总体架构

### 3.1 目录分层

当前代码按职责拆分为五层：

1. `rag/cli/`：命令入口层，只承接参数解析和运行调用
2. `rag/preprocess/`：原始文档预处理层
3. `rag/indexing/`：离线建库层
4. `rag/retrieval/`：在线检索、重排和答案生成层
5. `rag/shared/`：日志、检查点等共享基础设施

这种调整解决了原先“所有 Python 文件平铺在根目录、入口名与职责不一致”的问题。

## 4. 当前已实现能力分析

### 4.1 预处理链路

预处理链路继续保留原有输入治理能力：

- 识别 `doc/docx`
- 尝试直接解析 MHTML 风格内容
- 回退到 `soffice` 转 HTML
- 清理无关标签、隐藏节点和导出噪声
- 抽取图片资源并重写 HTML 引用
- 输出 Markdown 与来源映射清单

技术价值没有变化，但职责归位到单独目录后，后续更容易单独扩展图片处理、增量预处理或新输入格式。

### 4.2 离线建库链路

离线建库采用固定工作区内的文档级增量删后重建流程：

1. 扫描 `cleaned_markdown` 并计算 Markdown 文档内容指纹
2. 复用 `storage/index_workspace/` 中的索引产物和检查点，并对比 `checkpoints/document_index_state.json`
3. 清理变更和删除文档对应的旧 `node_id`
4. 只加载新增和变更文档
5. Markdown 语义切分并生成 `heading_path`
6. LLM 标注摘要、关键词和自由文本 `dependency_topics`
7. 按单文档聚合并校验全量直接依赖图
8. 正文、摘要及可选依赖关系向量化
9. 多路入库并重建 `metadata.json` 与 `bm25.pkl`
10. 校验 node、文档状态、BM25、metadata 和依赖图一致性，发布查询产物后原子更新 `manifest.json`

本次调整的主要改进点：

- 入口从含义模糊的 `main.py` 改为 [rag/cli/build_index.py](D:/ai/project/rag/rag/cli/build_index.py)
- 预览生成独立为 [rag/indexing/preview_renderer.py](D:/ai/project/rag/rag/indexing/preview_renderer.py)
- 默认建库不再全量重建全部 Markdown，未变化文档复用已有检查点与索引分片；只有标注或依赖图输出协议对应的 prompt 版本变化时才全部重新标注和建图
- 标注与依赖聚合检查点的缓存身份由内容和 prompt 版本决定，不包含模型名；成功记录通过 `model` 字段记录实际使用模型，因此切换模型不会触发重复调用
- 变更文档会先删除旧向量、旧检查点和旧 metadata 分片，再重建该文档全部 chunk
- 删除文档会自动清理旧 `node_id`，避免 Chroma、BM25 和 metadata 残留
- `chunk_previews/` 按文档输出预览页，便于排查召回和引用来源
- 失败或不完整的依赖图不会发布；构建失败时在线查询继续使用 `manifest.json` 指向的上一完整目录
- `dependency_topics` 由 LLM 根据 chunk 原文自由概括，程序只负责字符串清洗、去重和最多 5 个的数量限制
- topic 是可选的解释与辅助向量信号，不作为依赖边有效性、最终索引完整性或文档增量失效条件；关系方向和性质由 `relation_type` 表达，精确取证依赖 `node_id`
- topic 的当前使用边界见 [dependency_topics规范.md](D:/ai/project/rag/docs/dependency_topics规范.md)

### 4.3 在线检索、重排与答案生成

当前在线链路已经形成完整闭环：

1. Query Rewrite
2. 三路召回
3. 候选聚合
4. 规则粗排
5. 依赖召回路由与动态 seed 选择
6. 一层必要依赖扩展和邻居扩展
7. LLM 精排
8. seed 与必要依赖上下文组装
9. 最终答案生成和引用来源输出

与重构前相比，最关键的变化是：

- 不再只输出结构化检索结果
- 新增 [rag/retrieval/answer_generator.py](D:/ai/project/rag/rag/retrieval/answer_generator.py)
- 由 [rag/retrieval/query_service.py](D:/ai/project/rag/rag/retrieval/query_service.py) 统一编排检索与回答
- 命令入口改为 [rag/cli/answer_query.py](D:/ai/project/rag/rag/cli/answer_query.py)

### 4.4 模型使用策略

模型、服务、召回和答案生成的完整参数表及准确默认值见 [configuration.md](D:/ai/project/rag/docs/configuration.md)。需要注意，当前 Embedding 配置不会自动回退到 LLM 的 Key 或 Base URL。

查询侧统一围绕 `qwen3.6-plus` 配置：

- Query Rewrite：`RAG_QUERY_REWRITE_MODEL`
- LLM 精排：`RAG_RERANK_LLM_MODEL`
- 最终答案生成：`RAG_ANSWER_MODEL`

默认值全部为 `qwen3.6-plus`，满足“查询使用还是 qwen3.6-plus”的要求。

## 5. 核心数据结构分析

### 5.1 TextNode

离线切分后的 chunk 节点，关键字段包括：

- `id_`
- `text`
- `metadata`

其中 `metadata` 承载：

- 文档来源
- 文件类型
- `chunk_index`
- `token_size`
- 语义标注字段：`summary`、`keywords`、`tags`、`type`、`coherence`
- 结构字段 `heading_path` 和自由语义字段 `dependency_topics`；后者通常为 0～3 个，普通说明性 chunk 允许为空

### 5.2 RetrievalCandidate

这是在线检索阶段的核心聚合单元，统一承接：

- 多路命中明细
- 粗排得分
- 精排得分
- 最终得分
- 是否邻居候选
- 中心 chunk 来源
- 是否为依赖证据及其 source node、可选 topic、关系类型和置信度

### 5.3 QueryResponse

这是新增的查询输出结构，统一承接：

- 原始问题
- 改写结果
- 最终答案
- 来源引用
- 全量候选
- Top 候选

这让在线查询从“调试型输出”升级为“业务可消费输出”。

## 6. 技术选型分析

### 6.1 LlamaIndex

继续用于文档与节点抽象，适合作为基础数据结构层。项目核心流程仍由自定义逻辑控制，而不是依赖默认流水线。

### 6.2 Chroma

继续作为本地向量库，适合当前原型与本地验证场景。未来若需要规模化，可平滑替换为 Qdrant、Milvus 等。

### 6.3 OpenAI 兼容接口

标注、改写、精排、答案生成和向量化仍统一走 OpenAI 兼容调用方式，优点是接口统一、切换成本低，但依然要注意：

- Base URL 与模型配置错位
- 兼容服务稳定性
- Key 管理

### 6.4 BM25 与自定义分词

保留路径、下划线、中划线、点号命名和中文复合词，是当前技术文档召回质量的重要保障。

## 7. 可观测性分析

当前可观测性设计已具备较完整基础：

- 阶段级日志
- 进度输出
- 检查点
- 结构化索引产物
- chunk 预览页
- 查询答案引用来源

其中本次新增的文档级状态和分片产物让排查路径更明确：

- `document_index_state.json` 可以确认某个 Markdown 文档当前绑定的 `node_id`
- `metadata_docs/` 可以按文档核对 metadata 是否已删旧重建
- `metadata.json` 仍作为查询侧兼容快照，由所有存活分片聚合生成
- `dependency_cards.json` 按单个文档保存全量 node 直接依赖关系、聚合状态和关系语义
- 根 `manifest.json` 的 `final_index_dir` 明确当前在线使用的完整索引目录
- `chunk_previews/` 可以和 `metadata.json`、查询结果、最终引用一一对应
- 方便人工排查“命中的是哪个 chunk”
- 方便定位邻居扩展与重复召回问题

## 8. 风险与问题

### 8.1 测试覆盖仍偏轻

虽然本次补了增量建库相关测试，但整体仍缺少：

- 检索聚合单测
- 精排解析单测
- 答案生成降级单测
- 端到端回归测试

### 8.2 索引一致性风险仍需关注

默认增量流程在固定 `index_workspace` 中清理和重建，不直接修改当前在线最终目录。失败时应检查工作区；根清单仍指向上一完整结果：

- `storage/manifest.json`
- `storage/index_workspace/checkpoints/document_index_state.json`
- `storage/index_workspace/dependency_cards.json`
- `storage/index_workspace/metadata.json`
- `storage/index_workspace/bm25.pkl`

查询端只解析 `manifest.json.final_index_dir`，不会读取 `index_workspace`。发布目录不再向 metadata、BM25、Chroma 或依赖卡片写入批次 ID。Windows 上旧查询进程可能继续占用上一发布目录，清理会延后，但它不会再被根清单选中。

根 `manifest.json` 记录已发布索引的 `embedding_model`。查询服务在初始化编码器前执行强一致校验：当前查询模型与建库模型必须完全相同；字段缺失或名称不一致均直接抛出异常。Embedding 模型切换必须全量重建索引，不能复用旧向量空间。

旧工作区检查点可使用 `python -m rag.cli.build_index --storage-dir ./storage --migrate-workspace-checkpoints` 迁移。迁移仅规范化 `index_workspace/checkpoints` 中的 JSONL key，并保留原模型字段。

### 8.3 服务化能力仍不足

当前项目已具备完整问答闭环，但仍是命令行原型，距离生产服务还缺少：

- API 封装
- 请求治理
- 缓存与限流
- 监控告警

### 8.4 LLM 依赖敏感

Query Rewrite、LLM 精排和答案生成依赖兼容 LLM 服务。若配置缺失或接口异常，虽然当前支持部分降级，但答案质量仍会受影响。

### 8.5 隐式依赖聚合的准确性风险

文档级依赖图由 LLM 根据同一文档的 chunk 全文、摘要和标题路径生成，依赖主题只作为可选提示。为降低误关联风险，聚合结果必须满足：

- 依赖双方属于同一个 `doc_id`
- 每个依赖目标都是实际存在的 `node_id`
- 无法确认的关系使用空数组
- topic 为空、变化或与 chunk 标注不一致时，不得据此丢弃其他字段完整的依赖边
- 在线通过 `node_id` 直接读取证据，不根据 topic 做无约束的全库搜索

完整方案见：[docs/隐式业务依赖漏召回解决方案.md](D:/ai/project/rag/docs/隐式业务依赖漏召回解决方案.md)
