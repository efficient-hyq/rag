# 问题诊断与优化方案

## 问题一：依赖分析无法识别加解密关系

### 根本原因

1. **切分导致语义割裂**
   - 当前切分逻辑 `markdown_chunker.py` 基于 `chunk_size=512` tokens 硬切分
   - 加解密说明章节可能被切成多个 chunk，导致完整的加密流程被分散
   - 后续接口 chunk 引用 "X-Crypto" 时，LLM 只看到部分加密说明，无法建立完整依赖

2. **依赖识别条件过于严格**
   - `dependency_graph_v4.md` 要求 "B 引用了 A 定义的实体 + B 未完整重复 A 的说明"
   - 当加密说明被切分后，某个 chunk 可能只包含 "DES 加密算法"，另一个 chunk 包含 "X-Crypto 请求头用法"
   - LLM 在分析时看到的是不完整的上下文，confidence 会降低或直接不建立依赖

3. **dependency_topics 标注不准确**
   - `annotation_v4.md` 要求标注 "当前 chunk 提供的依赖能力证据"
   - 如果加密说明被切分，第一个 chunk 可能标注 `["加密算法"]`，第二个标注 `["请求头规范"]`
   - 但接口 chunk 需要的完整主题是 `["加密流程", "X-Crypto 请求头"]`，导致主题匹配失败

### 具体场景示例

**原始文档结构：**
```markdown
## 加密说明
客户端接口加密流程：
1. des_key base64解码
2. DES ECB加密
3. 携带HTTP请求头X-Crypto，值为des

如果接口要求DES加密，则携带X-Crypto请求头...
```

**切分结果（假设 chunk_size=512 过小）：**
- chunk_0: `## 加密说明\n客户端接口加密流程：\n1. des_key base64解码\n2. DES ECB加密`
- chunk_1: `3. 携带HTTP请求头X-Crypto，值为des\n如果接口要求DES加密...`

**问题：**
- chunk_0 的 `dependency_topics` 可能只有 `["DES加密算法"]`
- chunk_1 的 `dependency_topics` 可能只有 `["X-Crypto请求头"]`
- 接口 chunk 引用 "X-Crypto" 时，LLM 看不到完整的加密流程，可能不建立依赖

## 问题二：关键 seed 被移除，无关 seed 进入

### 根本原因

1. **seed 选择只看 final_score，忽略语义相关性**
   - `select_dependency_seeds()` 只根据 `score_ratio=0.7` 选择高分候选
   - 但高分候选可能是**通用说明章节**（如"产品介绍"），而不是**依赖证据**
   - 真正的依赖证据（如"加密说明"）可能因为分数略低被 `score_ratio` 过滤掉

2. **干扰文档污染向量空间**
   - 用户提到"现有文档中有部分无效文档，也就是干扰文档"
   - 这些干扰文档的 chunk 可能在向量召回中排名很高（因为关键词重叠）
   - 但它们不是真正的依赖证据，导致无关 seed 进入

3. **没有强制依赖的校验机制**
   - 当前 `expand_dependency_candidates()` 会记录 `missing_count`（依赖证据缺失）
   - 但这只是警告日志，不会阻止查询继续进行
   - 如果关键 seed 没有被选中，其依赖证据自然无法召回

4. **topoN 实际上是 final_top_n=5 的硬截断**
   - `assemble_dependency_context()` 先取 `final_top_n=5` 的常规 TopN
   - 然后追加强制依赖证据（不受 TopN 限制）
   - 但如果 seed 没有进入 TopN，其依赖证据可能被遗漏

### 具体场景示例

**查询：** "生成订单接口如何接入加密？"

**召回结果（按 final_score 排序）：**
1. chunk_产品介绍 (score=0.95) - 干扰文档，高分但无关
2. chunk_生成订单接口 (score=0.92) - 正确，是主要内容
3. chunk_支付流程说明 (score=0.88) - 相关但不是加密依赖
4. chunk_加密说明_chunk0 (score=0.75) - **关键依赖证据，但被 score_ratio=0.7 过滤**
5. chunk_错误码说明 (score=0.72)

**seed 选择结果（score_ratio=0.7 * 0.95 = 0.665）：**
- ✅ seed: chunk_产品介绍 (0.95 >= 0.665) - **无关 seed 进入**
- ✅ seed: chunk_生成订单接口 (0.92 >= 0.665)
- ✅ seed: chunk_支付流程说明 (0.88 >= 0.665)
- ✅ seed: chunk_加密说明_chunk0 (0.75 >= 0.665) - **勉强通过**

**问题：**
- 如果 `chunk_加密说明_chunk0` 的分数是 0.65，会被过滤掉
- `chunk_产品介绍` 是干扰文档，浪费了 seed 配额

## 优化方案

### 方案 1：优化切分逻辑，保持语义完整性

#### 目标
- 保证前置规范章节（加密说明、签名说明、错误码等）不被切分
- 保证接口定义章节的完整性

#### 实现思路

**1.1 识别不可切分的语义块**

在 `markdown_chunker.py` 中增加"原子块"识别：
```python
def is_atomic_section(heading_path: str, blocks: list[str]) -> bool:
    """判断某个章节是否应该作为原子单元，不允许切分"""
    atomic_keywords = [
        "加密说明", "签名说明", "鉴权说明", "认证说明",
        "错误码", "状态码", "返回码",
        "初始化配置", "SDK初始化",
        "通用参数", "公共参数", "全局配置"
    ]
    return any(keyword in heading_path for keyword in atomic_keywords)
```

**1.2 动态调整 chunk_size**

- 原子章节：允许 chunk_size 自动扩展到 1024 tokens
- 普通章节：保持 512 tokens
- 大型原子章节（>1024 tokens）：按子章节切分，但保证每个子章节完整

**1.3 增强 heading_path 传递**

- 确保每个 chunk 的 `heading_path` 包含完整的层级路径
- 在依赖分析时，LLM 可以通过 `heading_path` 判断两个 chunk 是否来自同一语义单元

#### 代码改动

修改 `split_markdown_chunks()`:

### 方案 3：优化 seed 选择策略，过滤干扰文档

#### 目标
- 优先选择**有依赖能力证据**的 chunk 作为 seed
- 降低干扰文档的权重
- 确保关键依赖证据不被遗漏

#### 实现思路

**3.1 引入 "dependency_capability_score"**

在 `select_dependency_seeds()` 中增加依赖能力评分：
```python
def calculate_dependency_capability_score(candidate: RetrievalCandidate) -> float:
    """评估候选 chunk 作为依赖 seed 的潜力"""
    score = 0.0
    metadata = candidate.metadata
    
    # 1. dependency_topics 非空，+0.3
    topics = metadata.get("dependency_topics", [])
    if topics:
        score += 0.3
    
    # 2. heading_path 包含前置规范关键词，+0.4
    heading_path = metadata.get("heading_path", "")
    prerequisite_keywords = ["说明", "规范", "配置", "流程", "机制", "错误码", "认证", "签名", "加密"]
    if any(kw in heading_path for kw in prerequisite_keywords):
        score += 0.4
    
    # 3. chunk 类型是 "api"（接口定义），+0.2
    if metadata.get("type") == "api":
        score += 0.2
    
    # 4. 如果 heading_path 包含"介绍"、"概述"等通用词，-0.3（降权干扰文档）
    generic_keywords = ["介绍", "概述", "简介", "背景", "产品"]
    if any(kw in heading_path for kw in generic_keywords):
        score -= 0.3
    
    return max(0.0, min(1.0, score))
```

**3.2 混合排序策略**

修改 `select_dependency_seeds()` 的选择逻辑：
```python
def select_dependency_seeds(
    candidates: list[RetrievalCandidate],
    score_ratio: float = 0.7,
    max_seeds: int = 8,
    capability_weight: float = 0.3,  # 新增：依赖能力权重
) -> list[RetrievalCandidate]:
    eligible = [
        candidate
        for candidate in candidates
        if not candidate.is_neighbor
        and not any(hit.route in {"neighbor_expand", "dependency_graph"} for hit in candidate.hits)
    ]
    if not eligible or max_seeds <= 0:
        return []
    
    # 计算混合分数：final_score * (1-w) + capability_score * w
    for candidate in eligible:
        capability_score = calculate_dependency_capability_score(candidate)
        candidate.dependency_seed_score = (
            candidate.final_score * (1 - capability_weight) +
            capability_score * capability_weight
        )
    
    # 按混合分数排序
    eligible.sort(key=lambda c: c.dependency_seed_score, reverse=True)
    
    # 选择 seeds
    highest = eligible[0].dependency_seed_score
    threshold = highest * score_ratio
    seeds = []
    for candidate in eligible:
        if seeds and candidate.dependency_seed_score < threshold:
            break
        seeds.append(candidate)
        if len(seeds) >= max_seeds:
            break
    return seeds
```

### 方案 4：优化上下文组装策略，避免信息截断

#### 目标
- 确保关键依赖证据不被 `final_top_n=5` 截断
- 根据查询意图动态调整上下文长度
- 提供依赖完整性校验

#### 实现思路

**4.1 引入 "强制依赖证据"机制**

修改 `assemble_dependency_context()`：
```python
def assemble_dependency_context(
    seeds: list[RetrievalCandidate],
    dependency_by_source: dict[str, list[str]],
    candidates: list[RetrievalCandidate],
    final_top_n: int = 5,
    max_forced_dependencies: int = 8,  # 新增：强制依赖证据的最大数量
    ensure_seed_in_context: bool = True,  # 新增：确保 seed 进入上下文
) -> list[RetrievalCandidate]:
    by_id = {candidate.node_id: candidate for candidate in candidates}
    result: list[RetrievalCandidate] = []
    seen: set[str] = set()
    
    # 第一步：确保 seeds 进入上下文（如果它们是高分候选）
    if ensure_seed_in_context:
        for seed in seeds[:final_top_n]:
            if seed.node_id in by_id:
                result.append(seed)
                seen.add(seed.node_id)
    
    # 第二步：补充常规 TopN（去重）
    for candidate in candidates[:final_top_n]:
        if candidate.node_id not in seen:
            result.append(candidate)
            seen.add(candidate.node_id)
    
    # 第三步：追加强制依赖证据（按 seed 顺序，受 max_forced_dependencies 限制）
    forced_count = 0
    for seed in seeds:
        for dependency_id in dependency_by_source.get(seed.node_id, []):
            if dependency_id in seen or dependency_id not in by_id:
                continue
            if forced_count >= max_forced_dependencies:
                logger.warning(f"强制依赖证据达到上限 {max_forced_dependencies}，停止追加")
                break
            result.append(by_id[dependency_id])
            seen.add(dependency_id)
            forced_count += 1
        if forced_count >= max_forced_dependencies:
            break
    
    return result
```

**4.2 依赖完整性校验**

在 `HybridRetriever.retrieve()` 中增加校验：
```python
def retrieve(self, query: str) -> RetrievalResult:
    # ... 原有逻辑 ...
    
    if dependency_expansion is not None:
        top_candidates = assemble_dependency_context(...)
        
        # 校验：是否有关键 seed 的依赖缺失？
        missing_critical_deps = []
        for seed in dependency_expansion.seeds[:3]:  # 只检查前3个高分 seed
            expected_deps = dependency_expansion.dependency_by_source.get(seed.node_id, [])
            actual_deps = [c.node_id for c in top_candidates if c.node_id in expected_deps]
            if len(actual_deps) < len(expected_deps) * 0.5:  # 缺失超过50%
                missing_critical_deps.append(seed.node_id)
        
        if missing_critical_deps:
            logger.warning(
                "关键依赖证据不完整 | seed_node_ids=%s | 建议检查 total_limit 或 final_top_n 配置",
                missing_critical_deps
            )
    
    return RetrievalResult(...)
```

### 方案 5：增加干扰文档过滤机制

#### 目标
- 在索引构建阶段识别干扰文档
- 在召回阶段降低干扰文档的权重

#### 实现思路

**5.1 索引构建时标记低质量文档**

在 `semantic_annotator.py` 中增加质量评分：
```python
def annotate_quality(annotation: dict[str, Any], text: str) -> dict[str, Any]:
    """评估 chunk 的质量，识别干扰文档"""
    quality_score = 1.0
    
    # 干扰信号1：通用营销语言
    marketing_keywords = ["领先", "一流", "优质", "专业", "全方位"]
    if any(kw in text for kw in marketing_keywords):
        quality_score -= 0.2
    
    # 干扰信号2：缺少具体信息
    if len(annotation.get("keywords", [])) < 2:
        quality_score -= 0.1
    
    # 干扰信号3：coherence 低
    if annotation.get("coherence") == "low":
        quality_score -= 0.2
    
    # 干扰信号4：没有依赖能力证据且 type 是 text
    if not annotation.get("dependency_topics") and annotation.get("type") == "text":
        quality_score -= 0.1
    
    annotation["quality_score"] = max(0.0, min(1.0, quality_score))
    return annotation
```

## 总结

两个核心问题的根源：

1. **依赖分析失败**：切分 + prompt 不够智能 → 语义割裂 → 无法识别结构性依赖
2. **seed 选择不准**：只看分数 + 干扰文档 → 关键证据被过滤 + 无关 seed 进入

优化策略的核心思路：

1. **保持语义完整性**：识别原子章节，避免切分前置规范
2. **增强依赖识别**：通过 heading_path 和 dependency_topics 建立跨 chunk 依赖
3. **智能 seed 选择**：混合 final_score 和 dependency_capability_score
4. **过滤干扰文档**：在索引和召回两个阶段降低低质量文档的权重
5. **动态上下文组装**：确保关键依赖证据不被 final_top_n 截断
