# 隐式业务依赖漏召回解决方案

## 1. 方案结论

当前 RAG 已具备正文向量、摘要向量、BM25、Query Rewrite、邻居扩展和双阶段重排能力，但这些能力主要解决“用户表达与 chunk 表述不同”的问题，不能稳定发现分散在同一文档不同位置的隐式业务依赖。

本方案不引入知识图谱，也不区分主流程节点和依赖节点。核心做法是：

1. 每个 chunk 只新增一个依赖主题字段，避免复杂语义标注。
2. 按单个 Markdown 文档聚合所有 chunk，生成完整的 node 依赖图。
3. 依赖图中的每个 node 都必须存在；没有依赖的 node 使用空数组。
4. 在线先执行现有普通混合召回，再根据普通召回得到的 `node_id` 查找依赖 node。
5. 通过依赖边上的规范化 topic 做展示、日志、覆盖检查和依赖关系向量化。
6. 通过依赖 `node_id` 直接从 metadata 读取证据 chunk，不再根据 topic 做全库模糊搜索。

最终链路如下：

```text
Markdown 文档
    ↓
chunk 切分与标题路径解析
    ↓
chunk 自动标注 dependency_topics
    ↓
按单个文档聚合全部 node 依赖关系
    ↓
生成 dependency_cards.json
    ↓
生成可选 dependency_vec

用户问题
    ↓
普通混合召回
    ↓
得到 seed node_id
    ↓
查询 node_dependencies
    ↓
直接补充依赖 node_id
    ↓
从 metadata 读取依赖 chunk
    ↓
去重、重排、上下文组装
    ↓
答案生成与来源输出
```

## 2. 问题边界

典型问题如下：

```text
怎么接入支付？
如何实现支付回调？
订阅接入有哪些步骤？
这个服务上线前需要配置什么？
```

用户问题通常只命中主任务对应的 chunk，但完整实现还需要参考签名、验签、幂等、证书、权限、错误处理等内容。这些内容可能位于：

- 同一文档的不同章节；
- 相距较远的 chunk；
- 与用户问题词面相似度较低的 chunk。

当前邻居扩展只能按 `doc_id + chunk_index` 找前后 chunk，无法覆盖跨章节依赖。因此需要在离线阶段建立文档内部的依赖关系。

本方案只解决以下问题：

- 普通召回命中某个 chunk 后，补充该 chunk 依赖的证据 chunk；
- 让依赖关系可解释、可校验、可追踪；
- 降低接入类问题漏掉关键前置约束的概率。

本方案暂不解决：

- 文档完全没有描述的外部知识；
- 跨文档、跨系统的全局知识图谱；
- 自动判断所有业务事实是否正确；
- 多轮会话下的依赖关系变化。

## 3. 设计原则

### 3.1 node 依赖关系优先

在线精准召回依赖实际的 `node_id`，而不是依赖 topic 再做一次模糊搜索。

```text
node-1 -> node-5
```

表示：

> 理解或执行 node-1 描述的内容，需要参考 node-5。

### 3.2 topic 负责解释，不负责最终取证

topic 用于说明依赖类型，例如：

```text
node-1 -> node-5 -> request_signing
```

其中：

- `request_signing` 用于分类、展示、覆盖检查和向量化；
- `node-5` 用于读取实际证据内容。

### 3.3 文档是聚合边界

每次聚合只处理一个 Markdown 文档。依赖关系双方必须属于同一个 `doc_id`，不允许聚合模型直接跨文档建立关系。

### 3.4 保守建立关系

如果模型无法确认依赖关系，应输出空数组，而不是根据通用常识强行补充依赖。文档没有提供的内容，最终答案必须明确说明资料缺失。

### 3.5 兼容当前增量建库

文档内容发生变化时，删除该文档原有全部 node、依赖卡片和依赖向量，再基于新文档完整重建。未变化文档继续复用现有索引和依赖产物。

## 4. Chunk 标注设计

### 4.1 新增字段

只新增一个语义字段：

```json
{
  "dependency_topics": [
    "request_signing",
    "idempotency"
  ]
}
```

字段含义是：

> 当前 chunk 实际描述了哪些依赖主题。

它不描述当前 chunk 依赖哪个 chunk，也不直接生成 node 之间的关系。

现有字段继续保留：

- `summary`：用于摘要向量、聚合判断和答案降级展示；
- `keywords`：用于 BM25 和技术术语召回；
- `tags`：用于主题辅助判断；
- `type`、`has_code`、`coherence`：继续服务现有检索和质量判断。

### 4.2 结构字段

建议增加一个由程序自动生成的结构字段：

```json
{
  "heading_path": "支付接入 > 回调处理 > 回调验签"
}
```

`heading_path` 不调用 LLM，由 Markdown 切分器维护标题栈得到。它用于：

- 判断 chunk 所在章节；
- 辅助聚合模型理解文档结构；
- 防止把同一文档中的无关章节错误关联。

因此新增内容只有：

```text
程序生成：heading_path
LLM 自动标注：dependency_topics
```

不需要人工逐个标注 chunk。

### 4.3 自动标注规则

LLM 标注提示词必须要求：

1. 只分析当前 chunk，不判断 chunk 之间的依赖关系。
2. 只能从受控 topic code 中选择。
3. 原文没有对应内容时返回空数组。
4. 不根据通用常识补充原文不存在的依赖主题。
5. 最多返回 3～5 个 topic，避免标注过度发散。

示例输出：

```json
{
  "summary": "支付回调需要先完成签名验证，并避免重复处理",
  "keywords": ["支付回调", "验签", "重复通知"],
  "dependency_topics": [
    "callback_signature_verification",
    "idempotency"
  ]
}
```

当前 `SemanticAnnotator` 已经具备并发调用、检查点缓存和失败重试能力。新增字段应沿用现有标注流程，并升级 `prompt_version`，确保字段变化后缓存不会与新标注格式混用。

## 5. Topic 规范化

### 5.1 为什么需要规范化

以下表达实际上可能是同一依赖：

```text
回调验签
回调签名校验
通知验签
支付结果验签
```

如果直接保存原始字符串，会导致：

- 文档聚合时无法稳定合并；
- 覆盖检查结果不一致；
- 向量文本表达不稳定；
- 日志和统计出现大量同义 topic。

### 5.2 标准 topic

第一版只维护少量通用 topic：

| `topic_code` | `topic_name` | 典型表达 |
| --- | --- | --- |
| `authentication` | 身份认证 | 登录认证、身份校验 |
| `permission` | 权限控制 | 权限、授权、访问控制 |
| `request_signing` | 请求签名 | 参数签名、接口签名 |
| `callback_signature_verification` | 回调验签 | 通知验签、回调签名校验 |
| `encryption` | 加解密 | 加密、解密、密文处理 |
| `certificate` | 证书管理 | 公钥、私钥、证书轮换 |
| `idempotency` | 幂等处理 | 重复通知、重复入账、幂等 |
| `retry_timeout` | 重试与超时 | 超时、重试、退避 |
| `error_handling` | 异常处理 | 错误码、异常、失败处理 |
| `compensation` | 补偿处理 | 补偿、冲正、回滚 |
| `reconciliation` | 对账处理 | 对账、差异核对 |
| `risk_control` | 风控处理 | 风险控制、反欺诈 |

LLM 输出 `topic_code`，程序根据固定词表得到 `topic_name`。`topic_name` 不作为机器判断的主键，避免展示名称变化影响依赖关系。

无法归入标准 topic 时，第一版可以丢弃该 topic，但保留原始含义在 `summary` 和 `keywords` 中。只有经过验证后，才增加新的标准 topic。

## 6. 文档级依赖卡片

### 6.1 数据结构

建议将生成产物保存到当前 generation 的 `storage/generations/<generation_id>/dependency_cards.json`：

```json
{
  "schema_version": "dependency_graph_v3",
  "generation_id": "20260803T120000Z-a1b2c3d4",
  "documents": {
    "payment/paypal.md": {
      "status": "success",
      "doc_content_hash": "a1b2c3d4",
      "expected_node_count": 7,
      "processed_node_count": 7,
      "model": "qwen3.6-plus",
      "prompt_version": "dependency_graph_v1",
      "generated_at": "2026-08-03T12:00:00Z",
      "node_dependencies": {
        "node-1": [
          {
            "node_id": "node-5",
            "topic_code": "request_signing",
            "topic_name": "请求签名",
            "relation_type": "prerequisite",
            "required": true,
            "confidence": 0.96,
            "reason": "发起支付请求前必须完成参数签名"
          },
          {
            "node_id": "node-8",
            "topic_code": "callback_signature_verification",
            "topic_name": "回调验签",
            "relation_type": "constraint",
            "required": true,
            "confidence": 0.94,
            "reason": "处理支付结果前必须验证回调签名"
          }
        ],
        "node-2": [],
        "node-3": [
          {
            "node_id": "node-10",
            "topic_code": "idempotency",
            "topic_name": "幂等处理",
            "relation_type": "constraint",
            "required": true,
            "confidence": 0.93,
            "reason": "支付通知可能重复发送，需要避免重复处理"
          }
        ],
        "node-4": [],
        "node-5": [],
        "node-8": [],
        "node-10": []
      }
    }
  }
}
```

### 6.2 全量 node 要求

当前文档中的每个 node 都必须出现在 `node_dependencies` 的 key 中：

```json
{
  "node-1": ["..."],
  "node-2": [],
  "node-3": ["..."],
  "node-4": []
}
```

空数组表示当前 node 没有被识别出的直接依赖。不能通过缺少 key 表示“没有依赖”，否则无法区分没有依赖和聚合失败。

### 6.3 文档聚合状态

全量 node key 只能表达图结构是否完整，不能单独区分“确实没有依赖”和“聚合失败后被补成空数组”。因此每个文档必须保存独立的聚合状态：

- `success`：全部 node 已完成聚合并通过校验，可以在线使用；
- `partial`：只处理了部分 node，保留结果用于排查，但不能进入正式在线依赖扩展；
- `failed`：聚合调用或结果解析失败，不能生成可在线使用的空依赖图。

程序必须校验 `expected_node_count`、`processed_node_count` 和 `node_dependencies` key 数量一致。只有 `status=success` 且数量一致的文档才能发布到当前有效索引批次。`partial` 和 `failed` 文档应记录失败原因并进入重试，不能通过为所有 node 补 `[]` 后伪装成成功。

### 6.4 依赖边语义

每条依赖边除目标 `node_id` 和 topic 外，必须保存以下最小语义：

| 字段 | 含义 | 在线用途 |
| --- | --- | --- |
| `relation_type` | `prerequisite`、`constraint`、`failure_handling` 或 `follow_up` | 区分前置条件、强制约束、异常处理和补充阅读 |
| `required` | 是否属于回答当前 source node 时必须保留的证据 | 决定候选是否进入必要依赖组 |
| `confidence` | 聚合模型对该关系的置信度，范围为 0～1 | 过滤低置信关系并支持审核 |
| `reason` | 基于文档内容给出的简短关联原因 | 用于日志、审核和错误定位，不直接代替原文证据 |

第一版在线扩展只使用 `required=true` 且 `confidence >= 0.7` 的依赖边。`follow_up` 默认应设置为 `required=false`，不进入第一版必要依赖候选集。

### 6.5 直接依赖与传递依赖

`node_dependencies` 保存直接依赖关系：

```text
node-1 -> node-5
node-3 -> node-10
```

不在卡片中预先展开传递依赖：

```text
node-1 -> node-5 -> node-10
```

卡片中不预先展开传递依赖。第一版在线检索只扩展一层直接依赖；第二层传递扩展保留为后续评测证明有必要后再启用的能力。

### 6.6 聚合输入

聚合模型接收当前文档全部 node 的结构字段、语义标注和 chunk 全文。`summary`、`keywords`、`dependency_topics` 用于快速定位和辅助判断，`text` 用于核对依赖条件、适用范围、调用顺序和强制性：

```json
[
  {
    "node_id": "node-1",
    "chunk_index": 0,
    "heading_path": "支付接入 > 接入流程",
    "summary": "支付接入的整体流程",
    "keywords": ["支付", "下单"],
    "dependency_topics": [],
    "text": "# 接入流程\n\n商户创建支付订单后，需要按照签名规则生成请求签名，再调用支付接口。支付完成后，商户根据支付回调更新订单状态。"
  },
  {
    "node_id": "node-5",
    "chunk_index": 4,
    "heading_path": "支付接入 > 安全要求 > 请求签名",
    "summary": "调用支付接口前需要完成请求签名",
    "keywords": ["签名", "参数排序"],
    "dependency_topics": ["request_signing"],
    "text": "## 请求签名\n\n所有支付请求必须按照参数名排序，并使用商户密钥生成签名。签名校验失败时，支付请求不会被受理。"
  }
]
```

每个 node 的 `text` 都是必填字段，必须使用切分后的完整 chunk 原文，保留其中的 Markdown 标题、列表、代码块、表格和限定条件。不能只传摘要，也不能截取开头片段代替全文，否则容易丢失“必须”“仅当”“失败时”“指定版本”等决定依赖关系的关键信息。

聚合仍以单个 `doc_id` 为边界。长文档可以按章节分批分析，再在同一 `doc_id` 范围内合并，不能把不同文档放进同一次聚合；无论是否分批，每个进入当前批次的 node 都必须携带完整 `text`。

### 6.7 聚合输出约束

聚合模型只能输出 node 关系，不需要判断主流程节点或业务能力：

```json
{
  "node_dependencies": {
    "node-1": [
      {
        "node_id": "node-5",
        "topic_code": "request_signing",
        "relation_type": "prerequisite",
        "required": true,
        "confidence": 0.96,
        "reason": "发起支付请求前必须完成参数签名"
      }
    ],
    "node-5": []
  }
}
```

程序负责补充 `topic_name`，并执行以下校验：

1. 依赖来源 node 必须属于当前文档。
2. 依赖目标 node 必须属于当前文档。
3. 不允许自身依赖。
4. 不允许重复边。
5. 不允许未知 topic code 直接进入正式卡片。
6. 所有文档 node 都必须出现在 key 中。
7. `relation_type` 必须属于允许枚举，`required` 必须是布尔值，`confidence` 必须位于 0～1。
8. `reason` 不能为空，并且只能概括文档中能够找到依据的关系。
9. 文档聚合状态和 node 数量校验必须通过。
10. 发现非法关系时丢弃该关系并记录日志，不阻断其他文档建库；如果处理 node 不完整，则整个文档标记为 `partial`，不能在线使用。

## 7. 依赖关系向量化

### 7.1 依赖向量的定位

依赖向量不是在线精确取证的主要依据。它用于：

- 用户问题直接命中包含依赖语义的 source node；
- 普通召回没有命中合适 source node 时提供兜底；
- 让依赖主题参与语义检索；
- 辅助分析哪些依赖关系容易被漏召回。

在线正常路径仍然是：

```text
普通召回 node_id
    ↓
node_dependencies
    ↓
依赖 node_id
    ↓
metadata
```

### 7.2 向量记录

建议以“存在依赖关系的 source node”为单位生成 `dependency_vec`：

```text
vector_id = source_node_id
```

向量化文本不应只包含英文 `topic_code`，而应包含中文 topic、source 摘要和依赖目标摘要：

```text
当前内容：支付回调处理。
章节：支付接入 > 回调处理。
依赖主题：回调验签、回调幂等。
相关依赖内容：处理支付结果前需要验证回调签名，并避免重复处理。
```

建议 metadata 至少包含：

```json
{
  "source_node_id": "node-3",
  "doc_id": "payment/paypal.md",
  "dependency_node_ids": ["node-8", "node-10"],
  "dependency_topic_codes": [
    "callback_signature_verification",
    "idempotency"
  ]
}
```

### 7.3 向量召回后的处理

如果 `dependency_vec` 命中 `node-3`，也不能直接把向量文本当作答案上下文。必须继续执行：

```text
dependency_vec 命中 node-3
    ↓
读取 node_dependencies[node-3]
    ↓
取得 node-8、node-10
    ↓
从 metadata 读取原始依赖 chunk
```

这样可以保证最终答案使用的是原始证据，而不是聚合摘要。

## 8. 在线检索流程

### 8.1 查询路由判断

不建议所有问题都执行依赖扩展。可以先通过规则判断，边界问题再调用 LLM。

通常需要依赖扩展的问题：

```text
怎么接入支付？
如何实现回调？
完整流程是什么？
上线前需要配置什么？
这个问题如何排查？
```

通常不需要依赖扩展的问题：

```text
merchant_id 是什么？
错误码 1001 表示什么？
这个接口返回哪些字段？
```

LLM 只负责输出：

```json
{
  "need_dependency_recall": true,
  "intent_type": "integration|procedure|lookup|troubleshooting|configuration",
  "confidence": 0.92
}
```

LLM 不负责临时决定依赖 node。具体依赖关系只能来自离线生成的 `node_dependencies`。

### 8.2 普通混合召回

无论是否执行依赖扩展，普通召回都应先执行：

1. 原始问题查询 `content_vec`。
2. 原始问题查询 `summary_vec`。
3. 原始问题查询 BM25。
4. 如果启用 Query Rewrite，对改写问题重复执行三路召回。
5. 以 `node_id` 聚合并去重。
6. 通过规则粗排得到 seed candidates。

依赖扩展使用粗排后与最高分候选仍处于同一相关区间的 node 作为 seed，不能只使用最终答案的 TopN，因为最终 TopN 截断可能已经丢掉可用于扩展的节点。

第一版使用以下简单规则动态选择 seed：

1. 粗排第一名候选始终作为 seed。
2. 后续候选分数不低于最高分的 70% 时继续作为 seed。
3. 出现明显分数断层后停止继续选择。
4. `neighbor_expand` 和 `dependency_graph` 路由产生的候选不能再次作为初始 seed。
5. 设置 8 个 seed 的安全上限，只用于异常查询熔断，不作为正常固定 TopK。

该规则使简单问题通常只产生少量 seed，复杂问题可以按实际相关性保留更多 seed。

### 8.3 根据 node_id 扩展依赖

假设普通召回得到：

```text
node-1、node-3
```

查询依赖图：

```json
{
  "node-1": [
    {
      "node_id": "node-5",
      "topic_code": "request_signing",
      "relation_type": "prerequisite",
      "required": true,
      "confidence": 0.96
    },
    {
      "node_id": "node-8",
      "topic_code": "callback_signature_verification",
      "relation_type": "constraint",
      "required": true,
      "confidence": 0.94
    }
  ],
  "node-3": [
    {
      "node_id": "node-10",
      "topic_code": "idempotency",
      "relation_type": "constraint",
      "required": true,
      "confidence": 0.93
    }
  ]
}
```

补充候选：

```text
node-5、node-8、node-10
```

依赖候选需要记录来源：

```json
{
  "node_id": "node-10",
  "route": "dependency_graph",
  "source_node_id": "node-3",
  "topic_code": "idempotency",
  "relation_type": "constraint",
  "required": true,
  "confidence": 0.93,
  "is_dependency_evidence": true
}
```

然后从 `metadata.json` 或内存中的 metadata 索引读取完整 chunk 内容。

### 8.4 第一版扩展边界

第一版只扩展 seed node 的一层直接依赖：

```text
node-1 -> node-5
```

依赖边必须同时满足：

- `required=true`；
- `confidence >= 0.7`；
- 目标 node 存在于当前有效 generation 的 metadata；
- 目标 node 尚未进入候选集，或者需要合并新的来源信息。

第一版不执行第二层传递扩展。单个 seed 最多补充 5 个必要依赖，普通候选和依赖候选合并后的总安全上限为 12。以上数量只作为异常数据熔断，不代表最终候选必须达到固定数量。

### 8.5 候选合并与上下文组装

普通候选和依赖候选以 `node_id` 去重。已被普通召回命中的依赖 node 只保留一份，但记录多个 route：

```json
{
  "node_id": "node-8",
  "routes": [
    "summary_vec",
    "dependency_graph"
  ]
}
```

最终候选不再统一执行 TopK 截断，而是按照以下顺序组成答案上下文：

```text
1. 保留动态选出的相关 seed node
2. 保留每个 seed 的一层必要依赖
3. 按 node_id 去重并合并 route、source node 和 topic 信息
4. 将完整结果交给答案生成器，不再由答案生成器执行固定 context_top_k 截断
```

如果合并后超过 12 个候选，按以下顺序裁剪：

1. 删除与已有候选 topic 和内容重复的依赖证据。
2. 删除 `confidence` 较低的依赖。
3. 删除分数最低的非首位 seed 及其独占依赖分支。

`required=true` 的依赖不能被普通候选的统一相关性排序静默淘汰。裁剪后仍无法容纳的必要依赖必须记录到日志中，不能假设答案已经获得完整证据。

上下文中可以附带关系标签：

```text
[普通召回] 支付接入流程
[依赖：请求签名] 请求签名规则
[依赖：回调验签] 回调验签步骤
[依赖：回调幂等] 重复通知处理方式
```

### 8.6 依赖缺失处理

如果卡片中记录了依赖 node，但该 node 在 metadata 中不存在：

1. 记录缺失 node 和 source node。
2. 在当前 `doc_id` 范围内使用 topic 和 summary 执行一次定向兜底召回。
3. 仍然找不到时，将该依赖标记为缺失。
4. 答案中明确说明当前文档未覆盖该依赖。

不能因为 topic 是 `idempotency`，就直接使用模型常识生成幂等方案。

## 9. 离线增量更新

### 9.1 新增文档

在新的索引 generation 暂存区执行完整流程：

1. 加载 Markdown。
2. 切分 chunk 并生成 `heading_path`。
3. 自动标注 `dependency_topics`。
4. 生成正文和摘要向量。
5. 写入 Chroma、BM25、metadata。
6. 聚合该文档全部 node 的依赖关系。
7. 生成该文档的 dependency vector。
8. 合并更新当前 generation 的 `dependency_cards.json`。
9. 校验当前 generation 内的向量、BM25、metadata 和依赖图一致性。
10. 校验通过后切换有效 generation。

### 9.2 变更文档

变更文档必须在新的 generation 中整体重建：

1. 从当前有效 generation 复用未变化文档的索引产物。
2. 在新 generation 中排除变更文档的旧 node、旧依赖图和旧 dependency vector。
3. 重新切分、标注、向量化和入库。
4. 重新生成该文档完整依赖图。
5. 完成全部一致性校验后切换有效 generation。

不能复用变更文档的旧依赖边，因为 chunk 文本变化可能导致 `node_id` 变化，旧边会指向过期 node。新 generation 构建失败时不得破坏当前有效 generation。

### 9.3 删除文档

删除文档时，在新的 generation 中排除：

- Chroma 中对应 node；
- `metadata_docs/` 对应分片；
- `dependency_cards.json` 中对应文档；
- `dependency_vec` 中对应 source node；
- 相关检查点记录。

完成新 generation 校验并切换后，旧 generation 可以按照保留策略延迟清理。不能先删除当前有效批次中的文档产物，再开始构建新批次。

### 9.4 索引批次与原子发布

`metadata.json`、`bm25.pkl`、Chroma 向量集合、`dependency_cards.json` 和可选 `dependency_vec` 必须携带同一个 `generation_id`，并作为一个完整索引批次发布。

建议的物理结构如下：

```text
storage/
  active_generation.json
  generations/
    20260803T120000Z-a1b2c3d4/
      metadata.json
      metadata_docs/
      bm25.pkl
      chroma/
      dependency_cards.json
      checkpoints/
```

构建和发布流程如下：

```text
创建新 generation 暂存目录
    ↓
生成全部索引产物
    ↓
执行 node、文档状态、依赖目标和 generation_id 一致性校验
    ↓
校验成功后原子替换 active_generation.json
    ↓
在线查询重新加载新 generation
```

一致性校验至少包括：

1. 当前 generation 中所有产物的 `generation_id` 一致。
2. `dependency_cards.json` 中只有 `status=success` 的文档可以在线使用。
3. 每个依赖 source node 和目标 node 都存在于同 generation 的 metadata。
4. dependency vector 引用的 source node 和目标 node 都存在。
5. 文档状态中的 node 数量与 metadata 和依赖图一致。

任何生成或校验步骤失败时，不更新 `active_generation.json`，在线查询继续使用上一完整 generation。旧 generation 至少保留一个可回滚版本，再按保留数量或时间策略清理。

## 10. 索引产物

建议新增以下运行产物：

| 产物 | 作用 |
| --- | --- |
| `storage/active_generation.json` | 指向当前在线使用的完整索引批次 |
| `storage/generations/<generation_id>/dependency_cards.json` | 保存文档级全量 node 依赖图 |
| `storage/generations/<generation_id>/dependency_vec` | 可选的依赖关系向量集合 |
| `storage/generations/<generation_id>/checkpoints/dependency_cards.jsonl` | 聚合检查点，支持失败重试 |
| `storage/generations/<generation_id>/checkpoints/dependency_vectors.jsonl` | 依赖向量检查点 |

`dependency_cards.json` 和 `dependency_vec` 属于索引运行产物，应与 `metadata.json`、`bm25.pkl` 和 Chroma 集合携带相同 `generation_id`，通过 `active_generation.json` 一次性发布，不应直接作为业务源码提交。

## 11. 可观测性

离线聚合阶段至少输出：

- 当前 `generation_id`；
- 文档数量；
- node 总数；
- 依赖边总数；
- 空依赖 node 数量；
- `success`、`partial`、`failed` 文档数量；
- 非法 node 数量；
- 非法 topic 数量；
- 非法关系语义字段数量；
- 被丢弃的依赖边数量；
- dependency vector 数量。

在线查询阶段至少输出：

- 普通召回 seed node 数量；
- seed 选择阈值和触发安全上限情况；
- 依赖扩展是否启用及原因；
- 依赖扩展层数；
- 补充依赖 node 数量；
- 每个依赖 node 的 source node、topic、关系类型、`required` 和 `confidence`；
- 去重数量；
- 候选总安全上限裁剪数量和原因；
- 缺失依赖数量；
- 最终上下文中普通候选与依赖候选数量。

业务日志通过 `rag/shared/logging_utils.py` 输出到 `stderr`，进度通过 `rag/shared/checkpoints.py` 的 `print_progress()` 输出到 `stdout`。

## 12. 验证方案

### 12.1 单元测试

至少覆盖：

- topic code 规范化；
- `node_dependencies` 全量 node 校验；
- 非法 node 过滤；
- 自身依赖和重复边过滤；
- 文档 `success`、`partial`、`failed` 状态校验；
- node 处理数量不完整时禁止发布；
- 聚合输入中每个 node 都包含完整且非空的 `text`；
- 关系类型、`required`、`confidence` 和 `reason` 校验；
- 依赖图一层扩展；
- 低置信和非必要依赖过滤；
- 基于最高分 70% 阈值的动态 seed 选择；
- 普通召回与依赖召回去重；
- 候选超过安全上限时按既定顺序裁剪；
- 缺失 node 的定向兜底；
- 文档变更和删除时依赖图清理；
- generation 一致性校验、原子切换和失败回滚。

### 12.2 专项评测集

建立接入类问题集，例如：

```text
怎么接入支付？
支付回调需要注意什么？
订阅回调重复通知怎么处理？
上线前需要配置哪些证书和密钥？
```

重点统计：

- 依赖 node 召回率；
- 关键依赖覆盖率；
- 依赖关系准确率；
- 无关依赖比例；
- 最终答案引用覆盖率；
- 依赖扩展带来的平均候选增长量；
- 查询延迟和 LLM 调用次数变化。

### 12.3 验收标准

方案实现后至少满足：

1. 每个文档的所有 node 都出现在依赖图中。
2. 无依赖 node 的值为 `[]`。
3. 聚合失败或 node 处理不完整的文档被标记为 `partial` 或 `failed`，不能在线使用。
4. 每条正式依赖边都包含合法的关系类型、`required`、`confidence` 和 `reason`。
5. 所有依赖目标都能在同一 generation 的当前文档 metadata 中找到。
6. 普通召回命中 source node 后，一层必要依赖可以被补充到候选集。
7. seed 按相对相关性动态选择，最终候选数量不由固定 TopK 决定。
8. 必要依赖不会因统一重排或答案生成阶段的固定 `context_top_k` 截断而丢失。
9. 超过安全上限时按照重复证据、低置信依赖、低分 seed 分支的顺序裁剪，并记录被裁剪的必要依赖。
10. 文档变更或删除后，新 generation 不会保留旧依赖边。
11. 新 generation 构建或校验失败时，在线查询继续使用上一完整 generation。
12. 文档没有相关依赖证据时，答案不会凭模型常识补全。

## 13. 实施顺序

### 阶段一：扩展结构和标注

1. 在 Markdown 切分时生成 `heading_path`。
2. 扩展标注 prompt，新增 `dependency_topics`。
3. 增加 topic code 规范化和校验。
4. 增加标注结果测试。

### 阶段二：生成文档依赖图

1. 按 `doc_id` 收集全部 node 及每个 node 的完整 chunk `text`。
2. 调用文档聚合 LLM 生成直接依赖边。
3. 补齐无依赖 node 的空数组。
4. 生成关系类型、`required`、`confidence` 和 `reason`。
5. 校验 node、topic、关系语义、文档状态和处理数量。
6. 将当前批次写入新 generation 暂存目录。
7. 完成所有索引产物一致性校验后原子切换 `active_generation.json`。

### 阶段三：接入在线依赖扩展

1. 在普通召回粗排后，按最高分 70% 阈值动态选择 seed node。
2. 加载并查询 seed 的一层 `node_dependencies`。
3. 只保留 `required=true` 且 `confidence >= 0.7` 的依赖边。
4. 根据 node_id 读取依赖 chunk。
5. 合并、去重并标记依赖来源。
6. 按 seed 在前、必要依赖在后的顺序组装答案上下文，不再统一执行固定 TopK 截断。
7. 候选超过 12 个安全上限时按既定顺序裁剪。
8. 增加缺失依赖、裁剪原因和扩展数量日志。

### 阶段四：补充依赖向量和评测

1. 生成依赖关系文本。
2. 写入 `dependency_vec`。
3. 将其作为普通召回未命中时的兜底路线。
4. 建立接入类专项评测集。
5. 根据评测结果调整 topic 词表和扩展限制。

## 14. 最终数据流

```text
离线：
Markdown
  → chunk + heading_path
  → LLM 标注 dependency_topics
  → 按 doc_id 聚合全部 node 及完整 chunk text
  → 生成带状态和关系语义的 node_dependencies
  → 写入新 generation 暂存目录
  → 可选生成 dependency_vec
  → 校验 metadata、向量、BM25 和 dependency_cards 一致性
  → 原子切换 active_generation.json

在线：
用户问题
  → 普通 content/summary/BM25 召回
  → 按相对相关性动态选择 seed node_id
  → 查询一层 node_dependencies
  → 补充必要且置信度合格的依赖 node_id
  → metadata 读取原始 chunk
  → topic 分组与展示
  → 去重、安全上限裁剪、上下文组装
  → 答案生成和来源输出
```

本方案的核心不是让 LLM 在在线阶段重新猜测依赖，而是把依赖关系提前固化为可校验的文档内 node 图，在线只根据普通召回结果沿图扩展，从而在保持现有 RAG 链路的同时补足隐式业务依赖。
