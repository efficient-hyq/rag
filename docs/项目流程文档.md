# 项目流程文档

## 1. 文档目标

本文档描述当前项目从原始文档输入到最终答案输出的完整执行流程，重点覆盖重构后的命令入口、目录分工、关键产物和排查路径。

## 2. 总体流程图

当前项目可以拆成三条主流程：

1. 文档预处理流程
2. 离线建库流程
3. 在线查询流程

整体关系如下：

```text
原始 doc/docx
    ↓
文档预处理
    ↓
cleaned_markdown
    ↓
chunk + heading_path + dependency_topics
    ↓
文档依赖图 + 多路索引
    ↓
工作区一致性校验与清单发布
    ↓
在线查询
    ↓
答案输出 + 来源引用
```

## 4. 离线建库流程

### 4.1 入口

- [rag/cli/build_index.py](D:/ai/project/rag/rag/cli/build_index.py)
- [rag/indexing/index_builder.py](D:/ai/project/rag/rag/indexing/index_builder.py)

示例命令：

```bash
.venv/Scripts/python.exe -m rag.cli.build_index --docs-dir "./storage/cleaned_markdown" --storage-dir "./storage"
```

### 4.2 默认增量行为

`build_index` 默认按 `cleaned_markdown` 中的 Markdown 文档做文档级增量建库：

1. 识别新增、变更、删除和未变化 Markdown 文档
2. 清理变更和删除文档的旧 `node_id`
3. 仅重建新增和变更文档
4. 基于当前全部存活文档重建 `metadata.json`、`bm25.pkl` 和依赖卡片
5. 在固定工作区校验通过后发布最终目录并原子更新根清单

发布时会把工作区构建清单中的 `embedding_model` 写入根 `manifest.json`。在线查询在创建编码器前严格校验当前模型与该值一致；不一致或旧清单缺失该字段时直接终止查询。

未变化文档会复用已有标注检查点、向量检查点、Chroma 节点和 metadata 分片。标注与依赖聚合成功检查点按内容和 prompt 版本命中，不依赖当前模型名；记录中的 `model` 字段仅用于追踪实际使用的模型。`document_index_state.json` 只记录标注 prompt 和依赖图 prompt 的输出协议版本；任一协议版本变化时，全部未变化文档转为待重建。topic 没有注册表或独立版本，其新增、改名和写法变化不会触发全量重建。

### 4.3 执行阶段

#### 阶段 1：识别增量文档

由 [rag/indexing/document_loader.py](D:/ai/project/rag/rag/indexing/document_loader.py) 负责：

- 扫描 `cleaned_markdown` 中的 Markdown 文件
- 计算每个 Markdown 文档的内容指纹
- 对比 `storage/index_workspace/checkpoints/document_index_state.json`
- 对比两个 prompt 的输出协议版本，协议变化时触发全量重建
- 输出新增、变更、删除和未变化集合

#### 阶段 2：清理旧索引

由 [rag/shared/checkpoints.py](D:/ai/project/rag/rag/shared/checkpoints.py) 和 [rag/indexing/storage_indexer.py](D:/ai/project/rag/rag/indexing/storage_indexer.py) 负责：

- 读取变更和删除文档旧状态中的 `node_id`
- 删除 Chroma `content_vec`、`summary_vec` 中的旧节点
- 清理旧 chunk、标注、正文向量和摘要向量检查点
- 删除对应 `metadata_docs/` 文档分片

#### 阶段 3：加载待重建文档

由 [rag/indexing/document_loader.py](D:/ai/project/rag/rag/indexing/document_loader.py) 负责：

- 只加载新增和变更 Markdown 文件
- 使用 `SimpleDirectoryReader` 加载为 `Document`
- 合并 `source_manifest.json` 中的来源元数据

#### 阶段 4：切分 chunk

由 [rag/indexing/markdown_chunker.py](D:/ai/project/rag/rag/indexing/markdown_chunker.py) 负责：

- 按标题、段落、表格、代码块进行语义切分
- 对超大文本块做二次拆分
- 补充 `chunk_index`、`token_size`
- 根据文档路径、chunk 序号、文本哈希生成稳定 `node_id`
- 维护 Markdown 标题栈并生成 `heading_path`

同时会写入：

- `storage/index_workspace/checkpoints/chunks.jsonl`
- `storage/index_workspace/chunk_previews/`

其中 `chunk_previews/` 会按文档输出预览页并展示：

- `chunk_index`
- `node_id`
- 文件名
- token 估算
- 摘要和关键词

#### 阶段 5：语义标注

由 [rag/indexing/semantic_annotator.py](D:/ai/project/rag/rag/indexing/semantic_annotator.py) 负责：

- 加载标注检查点
- 跳过已完成标注的 chunk
- 缓存命中不比较模型名，成功结果保留生成模型记录
- 并发调用 `qwen3.6-plus`
- 补充 `summary`、`keywords`、`tags`、`type`、`has_code`、`coherence`
- 自由标注 `dependency_topics`，仅描述当前 chunk 原文明确定义的依赖能力证据
- 程序只做空值过滤、字符串清洗、大小写无关去重和最多 5 个的数量限制，不校验固定词表
- 仅出现名词而没有规则、配置、约束或操作证据时保持空数组；具体使用边界见 [dependency_topics规范.md](D:/ai/project/rag/docs/dependency_topics规范.md)

#### 阶段 5.1：文档级依赖聚合

依赖聚合只以单个 Markdown 文档为边界：

1. 收集当前文档的全部 `node_id`、`heading_path`、摘要、关键词和 `dependency_topics`
2. 由 LLM 判断文档内部的直接 node 依赖关系
3. 更新工作区中的 `dependency_cards.json`
4. 补齐无依赖 node 的空数组
5. 校验依赖双方、关系类型、必要性、置信度、原因和处理数量；topic 仅作为可选说明字段

旧版检查点可通过 `python -m rag.cli.build_index --storage-dir ./storage --migrate-workspace-checkpoints` 迁移，操作范围仅为 `index_workspace/checkpoints`。
6. `partial`、`failed` 或 node 覆盖不完整的文档禁止发布

#### 阶段 6：向量化

由 [rag/indexing/embedding_client.py](D:/ai/project/rag/rag/indexing/embedding_client.py) 负责：

- 生成正文向量 `content`
- 生成摘要向量 `summary`
- 支持批量请求
- 支持检查点恢复
- 配置 `RAG_DEPENDENCY_VECTOR_ENABLED=true` 时生成可选 `dependency_vec`

#### 阶段 7：多路入库

由 [rag/indexing/storage_indexer.py](D:/ai/project/rag/rag/indexing/storage_indexer.py) 负责：

- 写入 Chroma `content_vec`
- 写入 Chroma `summary_vec`
- 写入 `metadata_docs/` 文档分片
- 聚合生成兼容查询侧的 `metadata.json`
- 基于全部存活 metadata 重建 BM25 索引
- 按文档重建 `dependency_cards.json`，同步清理变更或删除文档的旧依赖关系
- 校验工作区全部产物；成功后复制查询产物并原子更新根 `manifest.json`

最终产物：

- 构建与断点产物位于 `storage/index_workspace/`
- 在线产物位于 `storage/<manifest.final_index_dir>/`
- 根 `storage/manifest.json` 记录唯一有效的 `final_index_dir`
- 最终目录仅包含 `chroma/`、`bm25.pkl`、`metadata.json` 和 `dependency_cards.json`

## 5. 在线查询流程

### 5.1 入口

- [rag/cli/answer_query.py](D:/ai/project/rag/rag/cli/answer_query.py)
- [rag/retrieval/query_service.py](D:/ai/project/rag/rag/retrieval/query_service.py)

示例命令：

```bash
.venv/Scripts/python.exe -m rag.cli.answer_query "我要接入谷歌订阅，现在需要如何处理"
```

### 5.2 执行步骤

#### 步骤 1：加载配置与查询服务

`answer_query.py` 会：

- 从环境变量加载 [rag/config/retrieval.py](D:/ai/project/rag/rag/config/retrieval.py) 中的 `QueryConfig`
- 初始化 embedding 模型
- 初始化 Query Rewrite
- 初始化双阶段重排器
- 初始化答案生成器
- 组装 `QueryService`

#### 步骤 2：原始问题三路召回

[rag/retrieval/retriever.py](D:/ai/project/rag/rag/retrieval/retriever.py) 会执行：

- `content_vec` 向量召回
- `summary_vec` 向量召回
- BM25 召回

#### 步骤 3：Query Rewrite 扩召回

若启用 Query Rewrite：

- 使用 `qwen3.6-plus` 生成子查询
- 每个子查询重新执行三路召回
- 将结果合并进总命中集合

#### 步骤 4：候选聚合与规则粗排

- 以 `node_id` 为主键聚合多路命中
- 通过 RRF、多路命中奖励、改写命中奖励和完整度信号进行粗排

#### 步骤 5：邻居扩展

若开启相邻扩展：

- 围绕粗排前若干中心 chunk
- 按 `doc_id + chunk_index` 扩展前后相邻 chunk
- 为后续答案生成补足上下文

#### 步骤 5.1：依赖 node 扩展

依赖扩展以普通召回粗排后的 seed `node_id` 为入口：

1. 规则优先、LLM 兜底判断是否需要依赖召回
2. 按最高分 70% 阈值动态选 seed，最多 8 个
3. 查询 `dependency_cards.json` 中的一层 `node_dependencies`
4. 只保留 `required=true` 且 `confidence >= 0.7` 的边
5. 从 `metadata.json` 直接读取依赖 chunk，并合并 route 与来源信息
6. 单 seed 最多 5 个依赖，上下文总安全上限 12
7. 目标缺失时只在 source 所属文档内定向兜底，仍缺失则记录日志

`node_id` 负责精确取回依赖证据，`reason` 和摘要负责目标缺失时的同文档定向兜底；topic 只作为可选展示和同分排序信号。可选依赖向量命中的是 source node，仍需沿依赖图读取原始证据。

#### 步骤 6：LLM 精排

[rag/retrieval/ranking.py](D:/ai/project/rag/rag/retrieval/ranking.py) 会对头部候选做 LLM 精排，默认模型同样为 `qwen3.6-plus`。

必要依赖不会因精排顺序被静默淘汰。依赖路由启用时，答案上下文先保留全部动态 seed，再追加一层必要依赖；答案生成器不再执行固定 `context_top_k` 截断。

#### 步骤 7：答案生成

[rag/retrieval/answer_generator.py](D:/ai/project/rag/rag/retrieval/answer_generator.py) 会：

- 取 Top chunk 作为上下文
- 为每个 chunk 附带文件名、chunk 序号和 `node_id`
- 调用 `qwen3.6-plus` 生成最终答案
- 要求答案末尾附带参考来源

#### 步骤 8：结果输出

命令行最终输出：

- 原始问题
- 改写结果
- 最终答案
- 引用来源（文件名、chunk 序号、`node_id`、分数）
- TopN 候选详情

## 6. 核心配置对流程的影响

全部命令行参数、环境变量、准确默认值和覆盖优先级统一维护在 [configuration.md](D:/ai/project/rag/docs/configuration.md)。本节只保留直接影响流程结构的核心配置，避免与完整参数表重复。

| 配置 | 影响 |
| --- | --- |
| `RAG_CHUNK_SIZE` | 影响切分粒度 |
| `RAG_CHUNK_OVERLAP` | 影响上下文连续性 |
| `RAG_ANNOTATOR_MODEL` | 影响离线语义标注模型 |
| `RAG_QUERY_REWRITE_MODEL` | 影响改写模型 |
| `RAG_RERANK_LLM_MODEL` | 影响精排模型 |
| `RAG_ANSWER_MODEL` | 影响答案生成模型 |
| `RAG_RETRIEVAL_NEIGHBOR_ENABLED` | 是否启用邻居扩展 |
| `RAG_ANSWER_CONTEXT_TOP_K` | 兼容保留；当前答案生成使用检索器已组装的完整上下文 |
| `RAG_DEPENDENCY_RECALL_ENABLED` | 是否启用依赖路由与图扩展 |
| `RAG_DEPENDENCY_SEED_SCORE_RATIO` | 动态 seed 相对最高分阈值，默认 `0.7` |
| `RAG_DEPENDENCY_MAX_SEEDS` | seed 安全上限，默认 `8` |
| `RAG_DEPENDENCY_MIN_CONFIDENCE` | 依赖边最低置信度，默认 `0.7` |
| `RAG_DEPENDENCY_PER_SEED_LIMIT` | 单 seed 依赖安全上限，默认 `5` |
| `RAG_DEPENDENCY_TOTAL_LIMIT` | seed 与依赖上下文总上限，默认 `12` |

## 7. 常见运行顺序

### 第一次建库

1. 预处理原始 Word/Confluence 文档
2. 检查 `cleaned_markdown` 内容
3. 执行离线建库
4. 打开 `chunk_previews/` 中的文档预览页检查切分效果和 `node_id`
5. 执行完整查询验证答案与引用

### 文档更新后重建

1. 重新执行预处理
2. 重新执行离线建库
3. 未变化文档复用现有索引，新增和变更文档删旧后重建
4. 重跑典型问题做回归比对

## 8. 故障排查流程

### 8.1 预处理失败

优先排查：

- 原始输入目录
- `soffice` 可用性
- 原始导出格式是否合法

### 8.2 建库失败

优先排查：

- LLM Key / Embedding Key
- 标注失败数量
- 向量化失败批次
- Chroma 写入失败
- `document_index_state.json` 中变更或删除文档对应的 `node_ids`
- `metadata_docs/` 是否仍残留已删除文档分片
- `metadata.json` 和 `bm25.pkl` 是否已在本次运行后重建
- `dependency_cards.json` 是否覆盖当前文档的全部 node，依赖目标是否仍存在
- `manifest.json` 是否仍指向上一成功目录，`index_workspace` 中失败文档状态是否为 `partial/failed`

### 8.3 查询失败

优先排查：

- `storage/manifest.json` 是否存在且 `final_index_dir` 合法
- 清单指向目录中的 `chroma/`、`metadata.json` 和 `bm25.pkl` 是否存在
- `bm25.pkl` 是否存在
- 查询侧模型配置是否完整
- Query Rewrite、精排或答案生成接口是否异常
